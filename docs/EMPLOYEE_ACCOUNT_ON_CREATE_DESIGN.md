# An account for every employee added by hand — the design

> **Status: built, 2026-10-24.** The project
> owner: "creating an employee by hand also creates their account with a
> temporary password, returned once in the 201 response and shown once in the
> dashboard."

## 1. Why

The account model (`EMPLOYEE_APP_REQUIREMENTS.md` §7.1, ratified 2026-09-22)
says «كل موظف له حساب دخول»: attendance runs through the app, so an employee
without an account cannot be marked present, and payroll reads that as absence.
The import keeps the rule — every person it creates gets an account and a
temporary password (`EmployeeImporter::ensureAccount`). An employee added by
hand (`POST /api/hr/employees`) got none until someone with `auth.users.create`
made one on the Users screen, typing a password themselves.

## 2. The rule

- **`POST /api/hr/employees` creates the employee and their account in one
  transaction.** Either both exist or neither does.
- The account is the import's: linked to the employee, no email (contact, not
  identity), no role, `must_change_password` true (`UserService::create`, which
  logs `user_created`). The person signs in with their Kobo id.
- **The temporary password is generated by the server** — the import's
  alphabet and length (10 characters from `abcdefghjkmnpqrstuvwxyz23456789`, no
  look-alikes), one generator for both (`TemporaryPassword::generate()`).
- **It is returned once**, in the `201`, beside `data`:

  ```json
  {
    "success": true,
    "message": "تم إنشاء الموظف وحساب دخوله.",
    "data": { "id": 412, "employee_number": "582974643", "...": "..." },
    "account": { "user_id": 98, "login": "582974643", "temporary_password": "k7mq2xbr9t" }
  }
  ```

  It is stored only as a hash, never logged or audited, and no endpoint returns
  it again. Lost → an administrator sets a new one on the Users screen.
- **Permission:** `hr.employees.create` is enough, as `hr.employees.import` is
  for the import. The account carries no role, so it grants nothing beyond what
  every account has.

**Decided by the project owner at review (2026-10-24):**

1. An employee created with a status other than نشط (terminated, suspended)
   still gets an account — the rule is "every employee" — but a terminated one's
   is created **disabled**, as termination would have left it, and its
   `temporary_password` is `null`: nobody needs to sign in with it. If they
   return, an administrator re-enables the account and sets a password.
   Suspended: created enabled, password returned; sign-in is refused while
   suspended anyway (`AuthService::login`).
2. The message becomes «تم إنشاء الموظف وحساب دخوله.».

## 3. The dashboard

After a successful create the employee form does not close: it shows one panel,
«تم إنشاء حساب الدخول», with the login (the Kobo id) and the temporary password,
each with a copy button, and the warning «انسخ كلمة المرور الآن — لن تظهر مرة
أخرى. يُطلب من الموظف تغييرها عند أول دخول.» Its one button, «تم», closes the
form. A `null` password shows «الحساب معطّل لأن الموظف منتهي الخدمة.» instead.

## 4. Errors

| Case | Result |
|---|---|
| the account cannot be created | the employee is not created either (one transaction); the error as today |
| a validation error on the employee | 422 as today; no account |

## 5. Testing

- Store creates exactly one account: linked, `must_change_password`, no email,
  no role, a `user_created` audit row; the response's password signs in with the
  Kobo id, and only then (another password does not).
- The password matches the generator's alphabet and length; it is not in the
  audit log, and `GET /api/hr/employees/{id}` and `GET /api/users/{id}` never
  return it.
- A terminated create: account disabled, `temporary_password` null.
- A failure creating the account rolls the employee back.
- Dashboard: the payload helper unchanged; the create action returns the
  account beside the employee; the panel renders the login and password and
  closes on «تم».
